## 第一轮并行任务（2026-10-30 用户确认）

本地 `codex/p1-data-probe` 执行 P1-A：读取真实页面，确定年份请求、数量来源与失败情况，取得依据后实现最小浏览器诊断路径。云端 `codex/p1-render-probe` 执行 P1-C：确定性 20 年数据与独立渲染原型。两者分别向 `main` 提 PR。

本地独占数据、GitHub 适配、扩展入口、manifest、主构建和全局计划文档。云端独占 `src/renderers/probe/`、`probes/rendering/` 及自己的任务/报告文档。共用 `DailyContribution` 保持只读；共享边界修改先协调。具体状态以各任务报告与 PR 为准。

云端没有用户本机 GitHub 登录会话。无法观察的已登录/私有贡献路径写入待验收清单；提供可由用户在本机扩展中复现的最小步骤，不复制 Cookie、Token 或浏览器配置。无需把这些限制扩大为所有云端开发都停止；P1-C 等独立工作可以在明确授权的后续任务中继续。

首轮各自交付实现、脱敏报告、必要验证及独立 PR，列出未完成的真实浏览器、身份或硬件项目。不能越过 P1-G 自动进入正式 City/Terrain MVP。

## 分支与交付

- 初始化 PR 未合入时，云端从 `codex/project-bootstrap` 出发，为 P1-A 建议使用 `codex/p1-data-probe` 分支，创建以初始化分支为 base 的堆叠 PR；初始化合入后再把 base 调整为 `main`。
- 如果云端启动时初始化已经合入，则从实际最新 `main` 开始。不更改仓库默认分支来绕开 PR，也不直接往 `main` 写功能。
- 每个 PR 说明行为、验证依据、实际结果、未验收范围；完成源码修改后必须提交、推送并创建或更新 PR。平台权限不足时准确记录阻塞，不能把本地 diff 称作 PR 已交付。
- 合入、商店发布、许可证选择及产品范围变更分别依照用户授权；创建云端任务不自动授予合入权限。

## 验证与状态维护

文档修改静态核对即可；配置、类型、资源加载改动编译受影响目标；请求、身份、缓存、交互和渲染改变验证直接完整路径。需要隔离测试时，先列出有依据的失败方式并先写测试，再实现；不在实现后补单元测试。

报告写入 `docs/reports/`，至少记录环境、输入或生成规则、可复现步骤、实际结果及局限。页面响应、截图、日志、生成数据、浏览器资料、缓存与构建放任务临时目录并清理，只长期保留报告。

工作包状态使用“未开始 / 实现中 / 已实现待验收 / 验证通过 / PR 已提交 / 已合入”分别描述。依赖条件不满足时，不把待验收工作标记完成。计划、PR 和报告同步更新，避免多处重复维护同一份详细任务清单。

## 收敛条件

数量不可可靠取得、身份不可确认或硬件预算不满足时，先记录具体失败和最小下一步；不添加 Token、后端、估算数量、收费功能或独立网站绕过限制。只有产品约束确需改变时再请用户确认具体方案。
